# flash 专用调优手册（12 条）
> 这份手册只服务一个模型：**DeepSeek-V4.1-Flash-1017**。
> 每一条都是"因为 flash 是这样，所以要这样做"——换成别的模型，一半会失效。

---

## 1. 首稿一次写全，改稿最小化

**因为 flash 有 384K 输出**（不是 8K、不是 32K），2000–3000 行单文件可以**一次吐完**。

- 首次生成：要求"一次性给出完整 index.html，5 个场景函数全部写完"
- 之后修改：**只允许改一个场景函数或一个常量**（防止 F4 整文件重写癖）

```text
❌ 分 5 次让我写 5 个场景 → 5 次都要重读上下文，变量名漂移、坐标重复
✅ 一次写全 → 之后每次只 patch 那 8 行
```

## 2. 风格包全文常驻，不要"按需读取"

**因为缓存命中只要 ¥0.02/M**——比 Opus 便宜约 70 倍。

把这三份**一次性塞进上下文开头**，不要中途"再读一遍文件"：
```
style-dna.md + ds-failure-modes.md + 选定的 styles/<风格>.md
```
成本 ≈ 每轮 ¥0.001，可以忽略。

## 3. 修图靠"看图"，不靠"回忆"

**因为 flash 带图像理解**，这是它相对 v4-pro 的独占能力。

固定回路（每改 3 处走一遍）：
```
render_frames --stills → read_image 看 3 张 → 说 3 个具体问题 → 只 patch 那几行
```
**看图的硬规则**：一次最多看 3 张。看多了 flash 会失焦，只记住最后一张。

## 4. 创意用高温度抽卡，代码用低温度

**因为 flash 的创意是短板，但它的方差也大**——方差大意味着"多抽几次能抽到好的"。

| 任务 | 温度 | 动作 |
|---|---|---|
| 选题角度 / 分镜创意 | **0.9** | 一次出 5 个方案，你挑 1 个 |
| 写代码 | **0.3** | 要稳，不要"灵光一现" |
| 改文案 | 0.7 | 保留句式，只换词 |

**静帧抽卡**：同一个镜头出 2–3 个方案各渲 1 帧，成本约 ¥0.1 —— 这是这套生态里性价比最高的动作。

## 5. 静帧 2 版起步，不要 1 版定稿

**因为 flash 第一次给的多半是"最安全"的那个**（对称、居中、平均）。

流程改成：
```
镜头 4 → 方案 A / 方案 B 各 1 帧 → 对比 → 选一个或"A 的构图 + B 的配色"
```
多花 10 分钟，画面差异比你换三次提示词都大。

## 6. 深夜和周末跑批量

**因为空闲时段是高峰价的一半**：工作日 9–12 / 14–18 是高峰，其余全天半价。

| 时段 | 一条 2 分钟片 |
|---|---|
| 高峰 | ¥6–10 |
| **空闲** | **¥3–5** |

批量渲帧不花 token（本机 CPU），**花钱的只有写代码和看图**——所以把"写+看图"安排在晚上。

## 7. 一次只让它做一件事

**因为 flash 的多任务并行会互相污染**。同一个回合里让它"改字幕 + 加动效 + 换配色"，
八成会改坏两个。

```text
❌ "把字幕改成 42px，另外那段曲线太细了，还有结尾加个署名"
✅ 一次一句，改完看图，再下一句
```

## 8. 上下文超过 60% 就开新会话

**因为长上下文里 flash 会开始"记混"**：忘记 F1（对称癖）禁令、把第 2 个场景的坐标写到第 4 个场景。

- 一个场景一个会话是最稳的
- 换会话时，把 `script.md` + `storyboard.md` + 当前 `index.html` 一起带上（有缓存，很便宜）

## 9. 用中文写指令，且写"数字"

**因为中文是它的强项，而"高级/好看/有质感"这类词它接不住。**

| 无效指令 | 有效指令 |
|---|---|
| "画面高级一点" | "主视觉重心左移 12%，留白从 30% 提到 45%" |
| "动效自然一点" | "改用 easeOutBack，过冲不超过 6%，时长 0.62 秒" |
| "颜色再克制些" | "删掉第二个强调色，全片只保留 #C9A96A" |

**规律**：凡是能写成数字的，就写成数字。

## 10. 每轮结束让它自报"改了哪几行"

**因为 flash 倾向于悄悄多改**（顺手"优化"你没提的地方）。

固定结尾问一句：
```
你刚才改了哪几行？有没有碰到别的场景函数？
```
然后 `git diff --stat` 对一眼。行数对不上就回滚。

## 11. 并发 4 还是 8 都行——**别指望调它加速**

> ⚠️ 本条原先是凭印象写的（"4 慢、8 最快、16 反而慢"），2026-10-22 实测后推翻。

实测条件：同一段 60 帧、1920×1080、纯 2D、18 逻辑核。

| 并发 | 4 | 8 | 12 |
|---|---|---|---|
| s/帧 | 0.56 | **0.54** | 0.57 |

**差距 ±5%，等于没有。** 瓶颈是"每帧一个 Chrome 进程"的启动 + 光栅化，不是并发数。

真正影响耗时的是**单帧渲染成本**：

| 片段 | s/帧 |
|---|---|
| 网格/文字段（12–14s） | 0.54 |
| 大范围发光段（23–25s） | 0.64（+18%） |

780 帧按 0.54–0.64 推算 ≈ **7–8 分钟**。

**但要留缓冲**：同一份代码在后台任务里跑出过 **24 分钟**（3 倍），原因未查明
（怀疑是进程优先级被降 / 杀软逐个扫描 780 个 PNG）。

**结论**：不要用"整片重跑"赶时间，用 `--start/--end` 局部重渲；
要真提速，去砍 `shadowBlur` 和粒子数量，别调并发。

## 12. 失败就重跑同一个 prompt，不要改 prompt

**因为 flash 的失败多是随机波动，不是理解错误**。

```powershell
# 一次不行，原样再来两次
node ..\..\pipeline\render_frames.mjs --stills 45
```
三次都崩，才说明是提示词问题（这时候去补 F 系列禁令）。

